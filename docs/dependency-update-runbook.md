# Dependency Update Runbook

This runbook governs Dependabot and manual dependency updates for SubShield. Dependency pull requests are never auto-merged or auto-deployed.

## Monitoring cadence

- npm production and development dependencies are checked weekly on Monday morning in `America/Los_Angeles`.
- GitHub Actions are checked monthly.
- Minor and patch version updates are grouped separately for production dependencies, development dependencies, and GitHub Actions.
- Major version updates remain individual pull requests and require deliberate migration review.
- Security updates remain individual pull requests so urgency, exploitability, and deployment risk can be assessed independently.
- A read-only scheduled workflow runs `npm ci` and a high-severity production dependency audit every Tuesday.

## Required review process

1. **Confirm the base and scope**
   - Rebase or refresh the update against the current `main` before final review.
   - Confirm the lockfile was generated by npm and matches `package.json`.
   - Reject unrelated application, pricing, billing, analyzer, regulatory, environment, or customer-copy changes.
   - For grouped updates, review every included dependency and its release notes separately.

2. **Assess risk**
   - Identify whether each update is security, patch, minor, or major.
   - Review official advisories, release notes, engine requirements, peer dependencies, and known breaking changes.
   - Treat framework, authentication, payment, database, PDF/OCR, native-binary, and build-tool changes as high attention even when SemVer labels them minor or patch.
   - Do not suppress a high or critical production audit finding merely to make a check pass.

3. **Require exact-head validation**
   Package and lockfile changes trigger SubShield's existing safeguards:
   - Analyzer Accuracy Benchmarks
   - Regulatory Grounding Foundation
   - Billing Runtime Readiness
   - Baseline Security Headers

   The final reviewed commit must pass all applicable checks, including locked installation, production dependency audit, TypeScript, analyzer/regulatory regressions, production build, and secret-free Preview build.

4. **Verify the Preview deployment**
   - Confirm Vercel built the exact final commit.
   - Confirm the deployment is `READY`.
   - Review build logs for the detected Next.js and Node.js versions, dependency installation, TypeScript, route generation, native-binary warnings, and environment-variable failures.
   - Perform targeted Preview smoke testing when deployment protection and available test credentials permit it.

5. **Obtain a fresh exact-head review**
   - Request an independent correctness and security review after the branch is frozen.
   - Resolve all applicable P1/P2 findings.
   - Re-request review after any code or lockfile change; do not rely on a stale review from an earlier head.

6. **Merge deliberately**
   - Use squash merge unless a documented exception requires preserving commits.
   - Verify the expected head SHA immediately before merge.
   - Never enable automatic merge for dependency pull requests.
   - A merge to `main` triggers a production deployment and must be monitored through completion.

7. **Verify production**
   - Confirm the production deployment is `READY` on the exact merge commit.
   - Review production build logs.
   - Smoke-test the public homepage, pricing, login, canonical redirect, static assets, and any feature directly affected by the dependency update.
   - Check runtime errors after release.
   - For billing, authentication, Supabase, Stripe, analyzer, OCR, or storage updates, perform the relevant authenticated acceptance tests before declaring launch readiness.

8. **Record and close**
   - Record the pull request, exact reviewed head, squash merge SHA, deployment ID, checks, review outcome, smoke tests, and any deferred follow-up.
   - Close the tracking issue only after production verification.

## Security update priority

High or critical production vulnerabilities take priority over routine launch polish. The response should:

1. identify the vulnerable installed path and affected versions;
2. use the smallest patched version compatible with the application;
3. preserve analyzer, regulatory, billing, authentication, and deployment behavior;
4. keep the production audit as a blocking gate;
5. deploy promptly after exact-head checks and review are clean.

## Runtime-version boundary

Node.js 24 is SubShield's primary CI and Vercel production major. Local development defaults to Node 24 through `.nvmrc`. The repository declares Node `>=22 <25`: Node 22 remains a temporary compatibility lane while it is supported, and Node 25 or newer is unsupported until a separate compatibility audit approves it.

Every dependency and runtime-sensitive update must retain:

- all primary exact-head workflows on Node.js 24;
- the explicit Node.js 22 compatibility workflow; and
- an exact-head Vercel Preview build on the configured Node.js 24.x production environment.

Do not change the supported runtime range, remove the compatibility lane, or adopt Node 25+ inside an unrelated dependency or feature pull request.
## Permissions and secrets

- Dependabot and audit workflows do not receive production secrets.
- The scheduled audit uses `contents: read` only.
- No workflow may auto-merge, approve, deploy, modify billing, or write repository issues without a separately reviewed need and narrowly scoped permission.
- Do not place production Stripe, Supabase service-role, OpenAI, Resend, or other secrets in Preview or Dependabot workflows.
